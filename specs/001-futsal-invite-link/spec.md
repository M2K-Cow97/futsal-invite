# Feature Specification: 풋살 초대장 링크 공유

**Feature Branch**: `001-futsal-invite-link`

**Created**: 2026-08-22

**Status**: Draft

**Input**: `docs/2026-08-08-design.md` + `docs/기획-목업-전체.png` 의 5화면 정적 기획을,
서버·DB 기반 링크 공유 앱으로 확장한다.

## 배경

원본 기획은 혼자 5개 화면을 넘기며 티켓 이미지를 저장하는 정적 페이지였다.
"초대장"인데 정작 초대할 상대가 없었다 — 만든 사람이 스스로 포지션을 고르고 끝난다.

이 스펙은 그 흐름을 둘로 쪼갠다. **주최자**가 경기를 만들어 링크를 얻고,
**초대받은 사람**이 그 링크에서 원본 목업의 장난 흐름(싫어 버튼 도망 → SIUUU → 포지션)을
그대로 겪은 뒤 참석자로 등록된다. 목업의 재미는 그대로 두고, 대상만 남에게 넘긴다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 초대받은 사람이 링크를 열고 참석한다 (Priority: P1)

카카오톡으로 받은 링크를 누르면 "나랑 풋살할래? ⚽" 화면이 뜬다.
"싫어."를 누르려 하면 버튼이 호날두 킥에 맞아 도망가고, 3번 시도하면 "포기해."로 바뀐다.
결국 "좋아! 🙌"를 누르면 SIUUU 화면이 터지고, 이미 정해진 경기 일정을 확인한 뒤
포지션을 고른다. 공격수를 고르면 호날두가 2단으로 막아선다.
마지막으로 자기 이름이 박힌 확정 티켓을 받고, 이미지로 저장할 수 있다.

**Why this priority**: 이게 앱의 존재 이유다. 이 흐름만 있어도 링크를 받은 사람은
전부 경험할 수 있고, 원본 목업의 재미가 100% 살아난다.

**Independent Test**: 시드 데이터로 초대장 1건을 DB 에 넣고 `/i/{slug}` 을 열면,
5개 화면을 끝까지 통과해 참석자 1명이 DB 에 기록되는 것으로 검증한다.

**Acceptance Scenarios**:

1. **Given** 유효한 초대 링크, **When** 링크를 열면, **Then** invite 화면에 주최자 이름과
   함께 "나랑 풋살할래? ⚽" 가 표시된다
2. **Given** invite 화면, **When** "싫어." 버튼에 마우스를 올리거나(데스크톱) 터치하면(모바일),
   **Then** 호날두 킥 애니메이션이 재생되고 버튼이 컨테이너 내 다른 좌표로 이동하며 클릭되지 않는다
2-a. **Given** 터치 기기(hover 없음), **When** 손가락이 버튼 근처로 다가가면,
   **Then** 닿기 전에 버튼이 피한다 (모바일에서도 "누르려 하면 도망간다" 느낌을 유지)
2-b. **Given** 버튼이 여러 번 도망친 상태, **When** 어느 위치로 이동하든,
   **Then** "좋아! 🙌" 버튼을 덮지 않아 수락 경로가 항상 열려 있다
3. **Given** "싫어." 회피 3회 누적, **When** 다음 회피가 발생하면, **Then** 버튼 문구가 "포기해." 로 바뀐다
4. **Given** invite 화면, **When** "좋아! 🙌" 를 클릭하면, **Then** siuuu 화면으로 전환되고
   같은 클릭 이벤트에서 사운드 재생이 시작된다 (브라우저 자동재생 정책 회피)
5. **Given** siuuu 화면, **When** "날짜 고르기" 를 클릭하면, **Then** matchday 화면에
   주최자가 정한 날짜·시간·구장이 **읽기 전용**으로 표시된다
6. **Given** matchday 화면, **When** "다음" 을 클릭하면, **Then** position 화면으로 전환된다
7. **Given** position 화면, **When** 미드필더/수비수/골키퍼를 클릭하면, **Then** 서버에 응답이
   저장되고 ticket 화면으로 전환된다
8. **Given** position 화면, **When** "공격수" 를 클릭하면, **Then** 팝업①("나랑 겹치는데…
   정말 할거야? 🤨")이 열리고 포지션은 아직 확정되지 않는다
9. **Given** 팝업①, **When** "그래도 할래" 를 클릭하면, **Then** 팝업②("영장류 GOAT 공격수는
   나뿐이야 🐐")가 열린다
10. **Given** 팝업②, **When** "돌아가기" 를 클릭하면, **Then** 팝업이 닫히고 position 화면으로
    돌아가며 포지션은 미확정 상태다 (= 공격수는 끝내 고를 수 없다)
11. **Given** 팝업①, **When** "안할께.." 를 클릭하면, **Then** 팝업이 닫히고 position 화면으로 돌아간다
12. **Given** ticket 화면, **When** "이미지 저장" 을 클릭하면, **Then** 티켓 카드가 PNG 로 다운로드된다

### User Story 2 - 주최자가 경기를 만들어 링크를 얻는다 (Priority: P1)

주최자는 첫 화면에서 날짜·시간·구장·자기 이름을 입력한다.
"초대장 만들기"를 누르면 공유 링크(`/i/{slug}`)와 관리 링크(`/m/{token}`)가 나온다.
공유 링크를 복사해 단톡방에 던진다.

**Why this priority**: Story 1 이 열 링크가 없으면 아무것도 시작되지 않는다.
Story 1 과 함께 P1 이지만, 구현 순서상 이것이 먼저다.

**Independent Test**: 폼을 채우고 제출하면 DB 에 초대장 1행이 생기고
두 개의 URL 이 화면에 표시되는 것으로 검증한다.

**Acceptance Scenarios**:

1. **Given** 홈(`/`), **When** 날짜·시간·구장·주최자 이름 중 하나라도 비었으면,
   **Then** "초대장 만들기" 버튼이 disabled 다
2. **Given** 네 값 모두 입력됨, **When** 제출하면, **Then** 초대장이 저장되고
   공유 링크와 관리 링크가 표시되며 각각 복사 버튼이 있다
3. **Given** 생성 완료 화면, **When** 공유 링크 복사를 누르면, **Then** 클립보드에 전체 URL 이 복사된다
4. **Given** 과거 날짜, **When** 제출하면, **Then** "지난 날짜예요" 안내가 뜨고 저장되지 않는다

---

### User Story 3 - 주최자가 참석자 명단을 확인한다 (Priority: P2)

관리 링크를 열면 누가 참석하는지, 포지션별로 몇 명인지 보인다.
새로 응답이 들어왔는지 새로고침으로 확인한다.

**Why this priority**: 없어도 초대는 성립한다(링크 받은 사람은 티켓을 받음).
하지만 주최자가 결과를 못 보면 실사용 가치가 크게 떨어진다.

**Independent Test**: 응답 3건을 시드로 넣고 관리 링크를 열면
명단과 포지션별 집계가 정확히 표시되는 것으로 검증한다.

**Acceptance Scenarios**:

1. **Given** 응답이 있는 초대장의 관리 링크, **When** 열면, **Then** 경기 정보와
   참석자 이름·포지션 목록, 포지션별 인원 집계가 표시된다
2. **Given** 응답이 0건, **When** 관리 링크를 열면, **Then** "아직 아무도 응답하지 않았어요" 가 표시된다
3. **Given** 잘못된 관리 토큰, **When** 접근하면, **Then** 404 가 반환되고 초대장 내용이 노출되지 않는다

---

### User Story 4 - 잘못된 링크와 중복 응답을 처리한다 (Priority: P3)

없는 링크를 열면 안내 화면이 뜬다. 같은 사람이 두 번 응답하면 최신 응답으로 갱신된다.

**Why this priority**: 엣지 케이스. 없어도 정상 흐름은 동작한다.

**Independent Test**: 존재하지 않는 slug 접근, 동일 이름 재응답을 각각 시도해 검증한다.

**Acceptance Scenarios**:

1. **Given** 존재하지 않는 slug, **When** `/i/{slug}` 를 열면, **Then** "초대장을 찾을 수 없어요" 화면이 뜬다
2. **Given** 이미 "민수" 로 응답한 초대장, **When** 같은 이름으로 다시 응답하면,
   **Then** 새 행이 생기지 않고 기존 응답의 포지션이 갱신된다
3. **Given** 지난 경기의 초대장, **When** 링크를 열면, **Then** 흐름은 그대로 진행되나
   matchday 화면에 "이미 지난 경기예요" 가 함께 표시된다

### Edge Cases

- 에셋(GIF/사운드/호날두 이미지) 부재 → 이모지·플레이스홀더 박스로 대체, 흐름 중단 없음
- 사운드 자동재생 차단 → 무음으로 진행, 에러 표시 없음
- Neon cold start(첫 요청 ~1초) → 로딩 상태 표시
- 이름 미입력 응답 → 이름은 필수. 비어 있으면 포지션 버튼 disabled
- html2canvas 실패 → "이미지 저장에 실패했어요" 안내, 화면 유지

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 날짜·시간·구장·주최자 이름을 받아 초대장을 생성하고, 공유용 slug 와 관리용 token 을 발급해야 한다
- **FR-002**: 시스템은 slug 로 초대장의 공개 정보(날짜·시간·구장·주최자 이름)를 조회할 수 있어야 한다. 관리 token 은 이 응답에 절대 포함되지 않아야 한다
- **FR-003**: 시스템은 slug 에 대해 참석 응답(이름 + 포지션)을 등록해야 한다
- **FR-004**: 시스템은 동일 초대장 내 동일 이름의 재응답을 새 행 생성 없이 갱신 처리해야 한다
- **FR-005**: 시스템은 관리 token 으로 참석자 전체 명단과 포지션별 집계를 조회할 수 있어야 한다
- **FR-006**: 시스템은 유효하지 않은 slug/token 에 대해 404 를 반환하고 어떤 데이터도 노출하지 않아야 한다
- **FR-007**: 클라이언트는 5개 화면(invite/siuuu/matchday/position/ticket)을 목업 순서대로 전환해야 한다
- **FR-008**: 클라이언트는 "싫어." 버튼 회피 인터랙션과 3회 후 문구 변경("포기해.")을 구현해야 한다
- **FR-008a**: 회피 인터랙션은 hover 가 없는 터치 기기에서도 동작해야 하며,
  회피한 버튼이 "좋아!" 버튼이나 다른 UI 를 가려 수락을 막아서는 안 된다
- **FR-009**: 클라이언트는 공격수 선택 시 2단 팝업을 띄우고, 어떤 경로로도 공격수가 확정되지 않게 해야 한다
- **FR-010**: 클라이언트는 티켓 카드를 PNG 로 다운로드할 수 있어야 한다
- **FR-011**: 초대 링크는 OG 메타태그(제목·설명)를 제공해 메신저 미리보기가 보이게 해야 한다
- **FR-012**: 서버는 모든 입력을 스키마 검증해야 한다 (이름 ≤ 20자, 구장 ≤ 50자, 포지션은 4개 값 중 하나, 날짜는 유효 범위)
- **FR-013**: 과거 날짜로는 초대장을 생성할 수 없어야 한다

### Key Entities

- **Invite** — 하나의 풋살 경기 초대장.
  `id`, `slug`(공유용 짧은 문자열), `manage_token`(관리용 비밀값),
  `host_name`, `match_date`, `match_time`, `venue`, `created_at`
- **Response** — 초대장에 대한 한 사람의 참석 응답.
  `id`, `invite_id`(→ Invite), `guest_name`, `position`(FW/MF/DF/GK),
  `created_at`, `updated_at`. `(invite_id, guest_name)` 이 유일해야 한다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 주최자가 홈에서 링크 생성까지 30초 이내에 완료할 수 있다 (입력 4개 + 버튼 1회)
- **SC-002**: 초대받은 사람이 링크를 열고 티켓을 받기까지 별도 설명 없이 완주한다
- **SC-003**: 5개 화면 전부가 모바일(390px)과 데스크톱에서 레이아웃 깨짐 없이 표시된다
- **SC-004**: "싫어." 버튼은 정상적인 클릭/탭 시도로는 눌리지 않는다 (데스크톱·터치 양쪽)
- **SC-004a**: 버튼이 몇 번 도망쳐도 "좋아!" 는 항상 누를 수 있다
- **SC-005**: 공격수는 어떤 경로로도 최종 선택되지 않는다
- **SC-006**: A 가 응답한 뒤 주최자가 관리 링크를 새로고침하면 A 가 명단에 보인다
- **SC-007**: 전체 스택이 무료 티어 한도 내에서 동작한다 (카드 등록 없음)

## Assumptions

- 사용 규모는 지인 단위(초대장 수십 건, 초대장당 응답 20건 미만)
- 초대받는 사람은 자기 이름을 직접 입력한다. 신원 확인은 하지 않는다
- 링크를 아는 사람은 누구나 응답할 수 있다. 이것이 의도된 동작이다
- 초대장 삭제/수정은 이번 범위에 없다 (필요 시 후속)
- 실시간 갱신 없음. 주최자는 새로고침으로 확인한다
- 에셋 파일(GIF/사운드/이미지)은 사용자가 나중에 제공하며, 없어도 동작해야 한다

## Out of Scope

- 회원가입·로그인·소셜 인증
- 초대장 수정/삭제, 응답 취소
- 알림(푸시·이메일·카톡 API)
- 정원 관리, 포지션별 인원 제한, 대기자
- 정산·회비, 경기 결과 기록
- 다국어. 한국어만
- 실시간 업데이트(WebSocket/SSE)
