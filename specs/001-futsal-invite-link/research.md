# Phase 0: Research

**Feature**: 001-futsal-invite-link | **Date**: 2026-08-22

원칙 IV(무료 티어를 벗어나지 않는다)를 만족하는 스택을 고르고,
그 선택이 만드는 제약을 어떻게 흡수할지 결정한다.

## 결정 1: 호스팅 + DB 스택

**결정**: Next.js on Vercel (Hobby) + Neon Postgres (Free)

**검토 대안**:

| 스택 | 무료 한도 | 장점 | 탈락 이유 |
|---|---|---|---|
| **Vercel + Neon** | Vercel Hobby 무제한 배포 / Neon 0.5GB | Next.js 일체형, 카드 불필요, 국내 응답 양호 | — (채택) |
| Cloudflare Workers + D1 | 10만 req/일 / D1 5GB | 슬립 0, 엣지 실행 | D1 은 SQLite — `ON CONFLICT` 는 되지만 Postgres 대비 로컬/프로덕션 환경 차이가 크고, Next.js 통합이 Vercel 만큼 매끄럽지 않음 |
| Supabase 단독 | 500MB | 백엔드 코드 최소, 인증 무료 | 1주일 미사용 시 **프로젝트 일시정지** → 대시보드에서 수동 재개 필요. 지인용 앱은 몇 주 안 쓰는 게 정상이라 링크가 죽는다 |

**결정 근거**: Supabase 의 주간 일시정지는 이 앱의 사용 패턴(간헐적)과 정면으로 충돌한다.
Neon 은 유휴 시 compute 만 대기하고 첫 요청에 자동 복귀하므로 링크가 죽지 않는다.
D1 은 한도가 가장 넉넉하지만 원칙상 필요 없는 규모이고, Postgres 를 쓰면
`ON CONFLICT DO UPDATE` upsert(설계 결정 5)를 표준 문법 그대로 쓸 수 있다.

## 결정 2: Neon cold start 대응

**문제**: Neon Free 는 5분 유휴 후 compute 가 대기 상태로 간다.
복귀에 ~500ms~1s 가 붙어 첫 링크 열기가 느려진다.

**결정**: 서버 컴포넌트에서 조회하고, `loading.tsx` 로 스켈레톤을 보여준다.
프리워밍(크론 핑)은 하지 않는다 — 원칙 IV 가 크론을 금지하고,
무료 한도의 compute 시간을 낭비한다.

**대안 검토**:
- 크론으로 5분마다 핑 → 원칙 위반, 무료 compute 시간 소진. 탈락
- 클라이언트 fetch + 스피너 → 서버 컴포넌트보다 왕복이 하나 더 늘고 OG 태그 생성에 불리. 탈락
- **서버 컴포넌트 + loading.tsx** → 채택. Next.js 가 스트리밍으로 즉시 껍데기를 주고
  데이터가 오면 채운다. 체감 지연이 가장 작다

## 결정 3: 티켓 PNG 저장 방식

**결정**: `html2canvas` 를 티켓 화면 진입 시 동적 `import()`

**근거**: 원본 기획이 이미 `html2canvas` 를 지정했다(원칙 I — 기획 보존).
다만 ~200KB 라이브러리를 초기 번들에 넣으면 invite 화면 로딩이 느려지므로,
5번째 화면에 도달할 때 로드한다. 대안인 서버사이드 이미지 생성
(`@vercel/og`, satori)은 티켓 카드의 CSS 를 다시 작성해야 하고
무료 티어 함수 실행 시간을 쓴다. 클라이언트 캡처가 이 규모에 맞다.

## 결정 4: slug / manage_token 생성

**결정**: `nanoid` — slug 는 10자, manage_token 은 21자(기본값)

**근거**:
- slug 10자(64^10 ≈ 10^18): 카톡에 붙일 만큼 짧고 열거 공격이 무의미한 길이
- manage_token 21자 ≈ 125비트 엔트로피 → 원칙 V 의 "최소 128비트" 취지 충족
  (nanoid 기본 알파벳 64자 × 21자 = 126비트)
- UUID v4 는 36자로 URL 이 길고, 순차 ID 는 열거 가능해 탈락

## 결정 5: 입력 검증

**결정**: Zod 스키마를 `lib/validation.ts` 에 두고 Route Handler 진입부에서 `safeParse`

**근거**: 원칙 V 가 전량 스키마 검증을 요구한다. Zod 스키마를 단일 정의로 두면
클라이언트 폼 검증과 서버 검증이 같은 규칙을 공유해 불일치가 안 생긴다.

## 결정 6: 테스트 범위

**결정**: API 계약 테스트(Vitest) + 5화면 완주 E2E 스모크 1본(Playwright).
UI 애니메이션 단위 테스트는 작성하지 않는다.

**근거**: 헌법 개발 워크플로우가 "자동화 테스트는 API 계약에만" 으로 범위를 정했다.
다만 SC-004(싫어 버튼이 눌리지 않는다)와 SC-005(공격수 확정 불가)는
회귀하면 앱의 재미가 깨지는 핵심 불변식이므로 E2E 스모크에 포함한다.
애니메이션의 시각적 품질은 원본 기획대로 수동 확인(모바일 사파리 1회).
